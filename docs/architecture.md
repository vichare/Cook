# Architecture

## Boundaries

Cook is a same-origin web application: the browser loads React and calls `/api` on the same origin. Host nginx terminates TLS for `cook.vichare.net` and forwards only to `127.0.0.1:18080`. The Compose web container serves static assets and proxies `/api` to the private API container.

SQLite is the single source of truth. WAL mode, foreign keys, a five-second busy timeout, and bounded connection pooling are enabled at startup. Recipe ingredients are normalized as ordered AND groups containing ordered OR alternatives; optionality and group notes are stored separately, while `recipe_ingredients` remains a deprecated display projection for older clients. Every pantry and shopping-list query is scoped by `owner_id`. Automatic restock entries are derived only from opted-in concrete pantry items whose status is explicitly `out`; there is no group-level auto-restock. Manual and recipe sources are persisted and merged by concrete identity, while unresolved OR choices use an exact sorted identity-set key. Purchasing a choice requires one selected alternative and applies only that alternative to pantry. Marking an item purchased and undoing it preserve version, idempotency, and source snapshots in one transaction. Shopping deletion is separately versioned and idempotent: it removes every persisted source for exactly one concrete or choice item without mutating pantry or recipes; automatic-only items return an explicit disable-auto-restock outcome, and merged automatic items remain after persisted sources are removed. Delete replay records are bounded but deliberately advertise no undo because they are not state snapshots. Private recipes are visible only to their owner; another account may read or favorite a recipe only when it is public. Update and delete statements always include the authenticated owner.

## Authentication ports

Cook consumes `rust-web-auth-core`, `rust-web-auth-google`, `rust-web-auth-http`, `rust-web-auth-email-otp`, and `rust-web-auth-passkey` at exact revision `b087b47a3ba6fdcc04d67931e97c3214b82e5e6d`. Google Authorization Code OIDC, S256 PKCE, state, nonce, provider verification, secure cookie construction, sliding application sessions, Email OTP security policy, and WebAuthn verification come from the shared library.

Cook implements the consumer ports in SQLite:

- login attempts use insert-if-absent and one-statement `DELETE … RETURNING` consumption;
- existing identities resolve by `(issuer, subject)` first; a narrowly scoped first-login policy may attach a new Google identity to an existing Email OTP user only for an exact normalized `gmail.com` address;
- sessions persist only keyed token digests and use version-based CAS renewal/revocation;
- Google login starts use a 10-attempt, 15-minute SQLite rate-limit window keyed by a digest of the trusted client address;
- Email OTP stores one active challenge per purpose and normalized email, applies the shared ten-minute expiry, one-minute resend cooldown, five-attempt limit, atomic replace/verify/consume behavior, and persists separate email/IP and challenge/IP limiter buckets;
- passkey user handles and credentials are persistent, credential IDs are globally unique, and signature counters, backup state, last-used timestamps, names, and revocation are owner-scoped.

Cook owns its users, mappings, attempts, sessions, rate limits, database, keys, and Host-only production cookies. It does not accept or share SOP-Node cookies or databases. Email OTP identities use the issuer `urn:cook:email-otp`; an unauthenticated verified address creates or resolves only that identity. A Google-first user may link Email OTP only by completing a fresh OTP challenge for the exact normalized email stored on that Google identity. An email-first user may gain Google sign-in automatically only when a previously unseen Google subject reports the exact same normalized `gmail.com` address. The mapper does not apply Gmail dot folding, remove `+tags`, treat `googlemail.com` as `gmail.com`, or link a matching non-Gmail email-first account.

Google identity selection is rechecked inside the same SQLite transaction that creates or attaches the identity and inserts the Cook session. The `(issuer, subject)` primary key handles concurrent callbacks. If the Google subject and matching Email OTP identity already belong to different users, or if a matching non-Gmail email-first identity exists, Cook creates no user or session, records a PII-free audit event, and redirects to a generic recovery message. Existing accounts are never batch-merged or migrated; passkey handles and credentials stay on the canonical Cook user selected by the allowed linking rule.

Passkey registration requires an authenticated account with an explicitly linked Email OTP identity. Login is username-first through that identity. WebAuthn uses exact RP ID/origin validation and requires user verification. Non-serializable five-minute ceremony state remains in process memory; only a random opaque token is placed in a short-lived HttpOnly cookie. Restarting the process safely invalidates in-flight ceremonies without affecting credentials.

Production SMTP uses TLS and is configured only by environment variables. OTP codes and SMTP passwords are never logged. Development/test may use an explicit capture sender, but production cannot construct it. Request tracing records only method and path, never callback query strings, OTP codes, cookies, authorization headers, or SMTP credentials.

Development login is selectable only with `AUTH_MODE=dev` and a loopback bind. Production requires Google mode, exact HTTPS origin and passkey RP values, Google credentials, complete SMTP settings, and four distinct random digest keys for OAuth state, sessions, Email OTP, and passkey ceremonies. Incomplete configuration fails startup.

## Content moderation boundary

Moderation is a post-publication overlay. `recipes.publication_intent` is controlled by the author, `recipes.moderation_state` is controlled by moderation, and legacy `recipes.visibility` remains the effective compatibility field. Database triggers enforce `visibility = public` only when intent is `public` and moderation state is `clear`. The `public_eligible_recipes` view is the shared authorization predicate for every non-owner recipe and image read. A restricted owner may read and edit the recipe, including preserving public intent, but browser, AI-token, and legacy writes cannot clear the restriction.

Authorization is capability-based. Active `content_moderation` assignments are private account state returned only by `/api/me`; public recipe and author DTOs never expose them. Non-moderators receive 404 for `/api/admin/**`. Sensitive case evidence, restrict, reinstate, appeal resolution, and audit detail/export require a Passkey assertion bound to the current session from the last ten minutes. Google and Email OTP authentication alone do not raise this assurance. Assignment revocation increments the user's authorization version and deletes every session.

The first moderator is not selected by email or registration order. A trusted host command creates a random 15-minute one-time claim code, stores only its SHA-256 digest, and prints the plaintext once. An existing user with at least one Passkey enters the code in Cook and completes a fresh assertion; claim consumption, assignment creation, authorization-version change, current-session refresh, and audit append are one transaction. Host-only revocation accepts an assignment UUID.

Reports are available only to signed-in non-owners of current public-clear recipes. Reasons are stable enums, details are bounded plain text, duplicates use reporter + recipe + recipe version + reason, and the first report creates or reuses one open case with a bounded snapshot of then-public evidence. Every owner edit while a case is open or restricted refreshes the case's bounded current-version evidence and increments the case version, invalidating stale review, restrict, reinstate, or appeal decisions while preserving the owner's right to edit and appeal. Image evidence copies the normalized bytes, media type, and digest into the case snapshot with the same 2.5 MB stored-image ceiling; later public-ID rotation, reinstate, owner replacement, or owner deletion cannot alter it. Recipe deletion first transitions any active case and appeal to `content_removed` in the same transaction, then deletes the recipe, preventing image cascade triggers from clearing immutable evidence; any later failure rolls the entire transaction back. v0.6.0 performs no automatic time-based case purge: the immutable copy is retained for the case lifetime, and any future case-retention cleanup must delete the case so `ON DELETE CASCADE` removes the snapshot without leaving an orphan blob. Cases persist the original owner identity so self-moderation remains denied after recipe deletion. Moderator DTOs omit reporter identity and network data. A case-bound evidence-image endpoint reads only the immutable snapshot, requires fresh Passkey assurance and the same self-moderation check, returns `private, no-store`, and never grants moderator access through the ordinary recipe-image URL. One active appeal is allowed per restriction epoch. Enforcement mutations require same-origin requests, an `Idempotency-Key` bound to the action and target resource, optimistic recipe/moderation/case/appeal versions, and one transaction for state, image-ID rotation, case/appeal changes, owner notification, replay record, compatibility marker, and append-only audit. Reviewing or restricting a reported recipe requires exact current-version evidence; review atomically resolves the open case without action.

`moderation_audit_events` is an append-only operational ledger protected by SQLite update/delete triggers. It contains only opaque internal IDs, reason codes, versions, event type, and time; it excludes email, nickname, report/appeal message bodies, recipe bodies, IP addresses, cookies, Passkeys, and AI-token identity. After the first restriction, `release_compatibility.minimum_release` prevents deployment of binaries older than v0.6.0.

## Recommendation rules

The recommendation engine is deterministic:

1. Select candidates from enabled sources: saved recipes, owned recipes, favorite accounts' current public recipes, and other users' public recipes.
2. Apply hard filters before ranking: any excluded alternative removes a recipe; required filters must be assigned to distinct groups, so one group can satisfy at most one required filter.
3. Classify every group from the current user's pantry before deciding which optional groups become effective. Required groups are always effective; optional groups are excluded unless a must-use or scope-qualified desired assignment promotes them. Alternatives use the best pantry state in the order available, verify, missing:
   - recently confirmed, unexpired `have`: available;
   - expired or expiring-today `have`: verify with an explicit date reason;
   - stale `have` or `unknown`: verify;
   - absent or `out`: missing.
4. Assign each group one action with strict precedence `AVAILABLE > VERIFY > SHOPPING_PLANNED > MISSING`. Active concrete shopping items cover any exact alternative identity. Choice items cover a group only when their identity-set hash exactly equals that group's full alternative set. Owner pantry and shopping coverage are loaded in the same SQLite snapshot; another account's items never qualify.
5. Apply `ingredientScope`: `ANY` permits every action, `PANTRY_ONLY` permits only `AVAILABLE`, and `PANTRY_OR_LIST` permits `AVAILABLE` or `SHOPPING_PLANNED`. Verification alone never qualifies either restricted scope. Legacy `pantryOnly` maps to `PANTRY_ONLY`/`ANY`; sending it with `ingredientScope` is invalid.
6. Promote optional groups selected by distinct must-use assignment. Desired ingredients also use a maximum distinct-group assignment, but only across groups qualified by the selected scope; assigned optional desired groups become effective.
7. Classify fulfillment `READY > VERIFY > SHOP > BLOCKED`. Shopping-list coverage remains `SHOP`, not ready.
8. Sort with the deterministic `intent-v1` comparator. With desired ingredients: scope eligibility, desired action tier, desired matched count/coverage, fulfillment, unplanned missing ascending, shopping-covered ascending, verification ascending, effective groups ascending, source (`OWN > favorite > other`), available coverage descending, normalized title, then stable recipe ID. Without desired ingredients, the same order starts at scope eligibility and fulfillment. The bounded heap and final sort call the identical comparator.

Responses include available, verification, missing, and shopping-covered group labels; structured group actions and alternative evidence; an `intent-v1` ranking object with machine-readable reasons and applied scope; matched sources; and deprecated compatibility score fields. Legacy score fields are still populated but never participate in ordering. Saved-recipe and favorite-account overlap preserves both source labels while sharing one favorite source tier.

The recommendation endpoint returns at most 50 results by default and accepts a hard-capped `limit` up to 100. It scans every source-eligible candidate so top scores are not missed, but uses minimal candidate and batched projection/group queries, a bounded top-N heap, and one top-result hydration query for recipe bodies and image metadata. Selection, ingredients, ranking, and hydration share one SQLite read snapshot, hydration repeats the viewer/public visibility predicate, and a final current-visibility check discards recipes withdrawn before the response is serialized. Query count is constant with candidate count; the serialized response and expensive full-body hydration are bounded. Requests are also rate-limited by account and privacy-preserving IP partition.

Each account has an immutable random 128-bit public handle unrelated to its internal ID, email, or authentication identities. Public Cook-user profiles expose only that handle, the opt-in nullable nickname, and keyset-paginated public recipes. Favorite-account relationships are private and dynamically include the user's current and future public recipes; unpublishing immediately removes a recipe from that source. Existing `/authors/{handle}` routes and API field names remain stable compatibility identifiers, not user-facing terminology.

Ingredient hard identity is deliberately strict: an explicit canonical ID, a whole-term canonical name after Unicode NFKC/case/whitespace normalization, or an explicitly confirmed whole-term owner alias. Aliases compare for equality only and never expand through prefix, substring, or edit distance. Han, Kana, and Hangul never use edit-distance or substring matching; one-character Han prefixes are disabled. Canonical display-name prefixes remain advisory for Han queries of at least two characters. Latin typo suggestions require at least four characters, allow distance one for lengths 4–7 and at most two from length 8, and return at most two fuzzy results. Advisory selection binds only that submitted item and does not create an owner alias; an explicit non-advisory canonical confirmation may create one. Ambiguous exact/alias identities require an explicit canonical selection. The normalization pipeline also splits pasted comma, full-width comma, Chinese enumeration comma, semicolon, full-width semicolon, and newline lists.

Shopping purchase candidates use the same hard identity rules. A unique strict identity may be reused automatically; ambiguous strict matches require explicit `pantryItemId`; when no strict identity exists, an omitted `createUsingCurrentName` safely creates the submitted whole term. Nearby CJK terms such as `酱油`/`油` and `鸡腿`/`鸡翅` never become candidates for each other.

Suggestion candidates come only from the current account's pantry and recipes, visible public recipe ingredients, and that account's private aliases. Selecting a suggestion can create an owner-scoped alias; retaining the original input creates no alias. Pantry expiration is stored as ISO date-only text, and recommendation requests include the browser's local calendar date so “today” does not depend on server timezone. If an older client omits it, the API uses the server UTC date.

## AI recipe boundary

`LicensedRecipeImporter` accepts only structured recipes with source URL, license, and attribution. The included fixture returns no copied content. HowToCook prose and images are not stored in this repository.

The AI-client path is a separate, deliberately narrow boundary. The official skill uses browser or transcript capabilities already present in the user's client; Cook never fetches submitted source or image URLs. The default high-entropy token has only `recipes:import`. The private-management preset grants only `recipes:read`, `recipes:write`, and `recipes:images:write`. A third high-risk preset requires explicit risk confirmation and adds `recipes:publish`; it can create public recipes, publish owned private recipes, and directly update owned public recipes while preserving idempotency and optimistic concurrency. Existing tokens are never upgraded. No preset grants recipe deletion, pantry, account, or cross-account access. Every endpoint derives the owner from the token; cross-account recipe IDs return 404. Cook stores only the token's SHA-256 digest and non-secret prefix/metadata, supports expiry and revocation, uses persisted one-hour per-scope rate-limit buckets (20 import, 240 read, 600 recipe write, 300 image write, 60 publish, and 120 capability requests per token), and records token prefix/action/recipe audit metadata without authorization headers or recipe content.

All imported fields are untrusted and validated before persistence. Version 1 imports map every ingredient to one required group. Version 2 preserves explicit alternatives and optionality without inference, along with stable resource-local group/alternative IDs and provenance. Persisted group rows use server-generated primary keys plus resource-scoped external IDs, so reusable schema examples cannot collide across recipes, drafts, revisions, or accounts. Legacy-only updates cannot flatten an existing optional/OR recipe or draft. The deprecated single-alternative projection carries the alternative quantity note; the group note is not substituted for it. Drafts are owner-scoped, private, quota-limited, and retain source attribution, extraction warnings, and confidence. Web-session routes allow only that owner to list, edit, discard, or accept a draft. Acceptance creates a private recipe and marks the draft consumed in one SQLite transaction, preventing duplicate acceptance. The owner must use the normal recipe workflow for any later publication.

Management creates recipes with an `Idempotency-Key` and updates against an explicit recipe version. Private-management tokens create privately and store public changes as pending full-snapshot revisions; only the owner session can accept them. Publish tokens may request public visibility and mutate owned live public content directly, but use the same owner checks, validation, version conflicts, limits, and audit trail. Revision acceptance atomically checks the live version, applies text/ingredients/image changes, increments the version, and resolves the revision.

Interactive browser edits use the same optimistic recipe version invariant. Recipe content updates require `If-Match: \"recipe-v<version>\"`; every session cover upload, replacement, deletion, or metadata edit additionally requires an owner/recipe-scoped `Idempotency-Key` in `<unix-seconds>.<random>` form. An immediate SQLite write transaction serializes the first key lookup with the mutation, and the key plus normalized-operation fingerprint and resulting recipe version are committed atomically. Exact retries replay for 24 hours before rate-limit accounting; changed bytes, metadata, or operation return 409 before rate-limit accounting. Only a previously unseen key consumes the new-mutation allowance. Expired keys always return 409 and require a new key after reloading the recipe, which makes bounded cleanup safe. Cleanup removes at most 256 expired records per mutation, each recipe accepts at most 128 active replay records, and each owner is limited to 30 new session cover mutations per hour. The editor reuses the same cover key across retries and accepts replay only when its result version equals the freshly fetched recipe version; later body or cover changes retain the local form/file and use the conflict flow.

Each recipe has at most one cover image in `recipe_images`. Cook stores only a normalized JPEG BLOB plus random image ID, dimensions, SHA-256, alt text, source/license/attribution, and version. Uploads are limited to 8 MiB, JPEG/PNG/WebP magic-byte decoding, 20 megapixels, 10,000px decoder dimensions, 128 MiB decoder allocation, a 1,600px normalized longest edge, and 2.5 MB stored bytes. Re-encoding removes EXIF/GPS/ICC and other source metadata. Private image reads require the owner session or an owner token with `recipes:read` and use `private, no-store`. Public image reads use a strong ETag with `public, max-age=0, must-revalidate`; after unpublish or delete, revalidation of the old URL returns 404 instead of 304. Replacing an image or changing a public recipe back to private also rotates the random image ID. Deployments that add a CDN must preserve mandatory revalidation or provide verified purge-on-withdrawal; Cook cannot purge an independently misconfigured intermediary. SQLite BLOB storage keeps image data in the existing atomic backup. A future object-storage migration can preserve random IDs and metadata while moving bytes behind the same authorization layer.

## Public profile boundary

OIDC email, display name, issuer, and subject are private. Public recipe DTOs contain a nullable opt-in nickname and an `isOwner` flag instead of the recipe owner's UUID. Null is the stable anonymous state; localized anonymous labels exist only in the UI. Recipe queries join the current nickname dynamically so a profile change updates prior public recipes without rewriting recipe rows.

## Accessibility baseline

The web UI targets WCAG 2.2 AA with 16px or larger default text, 44px minimum control targets, high contrast, visible focus, keyboard operation, textual status cues, and layouts that reflow at 200% zoom. Ingredient suggestions use an ARIA combobox/listbox with active-option tracking and live announcements. Destructive credential, token, and draft actions require explicit confirmation.
